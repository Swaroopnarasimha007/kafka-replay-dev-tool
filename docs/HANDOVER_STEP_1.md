## Contracts and fixtures

See `API.md` for request/response shapes, role permissions, schema and header handling.
See `README.md` and `application-live.yml` for deployment configuration.
Profile credentials are AES-256-GCM encrypted, with distinct random 12-byte nonces;
separate replay principal credentials are stored but unused by browse. Only admins
can submit a connection test and save its successful, expiring single-use token.
Kafka diagnostics are suppressed to avoid credential-bearing client logs. Browse
and reveal attempts write actor/action/coordinates into `browse_audit` in live mode.

Default demo fixture: `orders.DLT`, partitions 0–2, offsets 0–19. Timestamps start
2025-01-01T00:00:00Z plus offset seconds; offset 3 contains bytes `00 ff 01`, offset
4 has null value, offset 5 has null key. Headers include two ordered `trace` values.
Example coordinates: `demo-cluster / orders.DLT / partition 0 / offset 3`.
Demo content is synthetic; it is never replayed to a real cluster.

Real local fixture is generated by `RealBrokerTest`, uses an ephemeral broker and
in-memory test database, and is destroyed afterward. It seeds raw bytes directly
in `orders.DLT`; offsets 0–19 in each partition, with offset 4 a tombstone.
The test checks a separately seeded `existing-application` group offset 7 on P0
before and after browsing. It does not leave a persistent cluster for manual UI use.

Headers are preserved as ordered name/base64 pairs, including all Spring Kafka DLT
header names. There is no envelope extractor yet. Raw record bytes qualify as
byte-preserving inputs only after step 2 explicitly selects a trusted raw/Spring DLT
extraction policy and destination mapping. Wrapped envelopes remain browse-only.
No record is currently marked approved or executable.
